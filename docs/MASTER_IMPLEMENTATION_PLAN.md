## 5. Identity, tenant context and access lifecycle

### Authentication and invitations

Invite-only, verified email/password; public signup, anonymous signin and domain auto-join remain disabled. A successful Auth account verification never creates membership by itself. K01 creates pending intent for the exact approved recipient and initial owner; K02 owner invitations can grant only operator. Platform grants cannot be assigned through invitations.

Persist operation UUID, actor, intended tenant/email/role, payload digest, idempotency key and reconciliation state before external Auth delivery. On an ambiguous Auth response, look up and reconcile the existing identity/delivery instead of blindly creating or sending again. Reuse existing Auth accounts. Acceptance requires verified identity/email from a trusted Auth boundary, live expiry check, issued/unrevoked invitation, exact recipient, role ceiling and required assurance. Lock tenant then invitation/membership state; consume invite, activate membership/initial tenant, append audit and commit receipt in one transaction. Expired open invitations must transition to expired before another invitation is issued; the unique open-email index must not be bypassed. A fresh replay of a consumed token is denied; an identical authenticated command retry may return its existing scoped receipt without consuming it again.

Pending tenants and nonmembers cannot satisfy the normal membership helper. Acceptance therefore needs a narrow pre-membership command policy that can inspect only the matching invitation and intended tenant, plus bootstrap activation rules. It must not grant public invitation reads or general membership insertion. First platform grant uses the approved custodian bootstrap runbook, never a public endpoint. Auth and database are separate systems; no distributed transaction or exactly-once email delivery claim.

Invitation issue, revoke, accept, login and recovery are abuse-sensitive entry points. P1C must use a durable server/Edge rate-limit mechanism keyed to the normalized recipient, authenticated actor/session and request origin/IP as appropriate, with redacted audit and fail-closed behavior during limiter failure. Exact windows, thresholds, lockout and user-facing retry copy are `OI08` owner inputs; no in-memory single-instance limiter or email-enumerating response is acceptable. Known and unknown email responses for login/recovery must be indistinguishable.

Acceptance must reject a suspended tenant, and a pending tenant may be activated only for its exact initial-owner path. A pending tenant recipient who is not the intended initial owner is denied. A previously revoked membership cannot be re-invited or silently revived until `OI09` records the owner's choice; testing the revoked denial path must not invent that choice.

### Sessions, MFA, recovery and logout

Session verification belongs in each DAL query and each action/handler/Edge entry. Cookie presence and unverified session objects are insufficient. Owner tenant access and platform administrative operations require `aal2`; operator content access requires verified identity and active membership. Required MFA enrollment/challenge must precede owner activation or access. Database and Storage paths must enforce the same assurance boundary; hiding screens is insufficient. The narrow identity lookup used to decide whether MFA is needed must not expose business data or recurse through its own policies. Prove initial-owner enrollment and platform bootstrap work without a circular membership prerequisite.

P1C must replace the role-agnostic assurance path with a role-aware helper/policy contract: for the requested tenant, an owner row requires `aal2`, an operator row may use `aal1`, and a platform-admin command requires `aal2` without granting tenant content. The additive migration may create new helper roles/functions and replace policies, but it must temporarily re-grant the helper-owner role to the migration runner only for the reviewed alteration, then revoke it and prove the final membership/grants. Direct Data API/RPC/Storage tests cover aal1/aal2 and mixed memberships; no UI-only MFA claim closes the gate.

Recovery uses the approved D05 provider/procedure, allowlisted callback origins and verified provider recovery flow; it restores identity only. It cannot create membership, revive revoked membership, unsuspend a tenant, reset MFA or transfer ownership implicitly. Failed/expired/reused recovery links get a safe localized outcome. MFA factor loss and privileged bootstrap recovery follow the supplied recovery/handover process; no invented bypass.

Logout revokes the selected provider session/refresh capability and clears app cookies and private client state; reload, back navigation and other tabs must not reuse the app's private cached response. Exact session scope follows D05's runbook. Already issued access-token lifetime is a separate provider limitation, not an immediate-global-revocation promise. Sensitive commands must check current session validity as required by that runbook; membership revocation/suspension must deny new reads even with an unexpired JWT. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions) and [MFA](https://supabase.com/docs/guides/auth/auth-mfa) inform implementation, not owner recovery policy.

### Tenant context and role enforcement

The selected tenant UUID in `/{locale}/t/{tenantId}` is an untrusted selector. Derive actor from verified Auth and role from current DB membership, validate tenant active status, then bind the adapter to this context. Every query includes tenant scope and same-tenant joins, with RLS authoritative. Never reuse tenant slug config as a database membership.

Explicit tenant deep links support multi-membership without inventing a tenant-picker page. Login returns only to an allowlisted validated intended tenant route; unknown, inaccessible or absent tenant context must use the approved access state, not silently choose a different organization's data. Locale switches preserve tenant and package; role never transfers with navigation. A platform admin without tenant membership sees no tenant content; with operator membership gets only operator authority. Viewer/machine subjects cannot inherit human access. `OI10` must confirm whether the Phase 1 operator read projection is identical to the owner's Today/package projection or enumerate the approved reduced fields; the plan does not infer equivalence from shared RLS reads.

Routine owner role mutation is deferred under D20. The restricted Phase 1 revoked-member test uses an auditable, time-bounded Abdo platform/custodian operation that can revoke an operator membership but cannot elevate, transfer ownership or grant content access; no tenant-owner membership screen or owner-facing revoke command is enabled. Platform suspension requires current platform grant/MFA. All membership writes share the tenant serialization lock and preserve the last active owner. Revocation yields localized denial on the next protected request, with safe logout/recovery and no stale content. No realtime push mechanism is inferred. Recovery and tenant reactivation are separate; reactivation tooling needs explicit operational scope before activation.

## 8. Server-side write and read authorization matrix

All contracts below are proposed; exact code files are in the phases. All mutations validate bounded versioned payloads, derive actor server-side, enforce origin/token rules, lock current authority and append redacted evidence. Public function EXECUTE is revoked unless deliberately granted to the exact caller role. Dedicated command owners must be NOLOGIN/NOBYPASSRLS, non-table-owner, least privilege with explicit RLS and fixed search path. Helpers remain separate read-only roles. Never disable RLS to make a command work.

| Operation | Entry / caller | Transaction and boundary |
| --- | --- | --- |
| K01 provision/suspend | Restricted Edge tooling; verified active platform admin at aal2 | G04 intent/progress, G03 platform audit, pending T01; suspension locks tenant and records audit/receipt; no business-content result |
| K02 issue/revoke invite | Owner at aal2 in active tenant; initial-owner path is platform-only | Tenant/issuer/role ceiling, T03 lifecycle, T04/T22; Auth issuance isolated in Edge saga, no activation on delivery |
| K02 accept invite | Verified exact recipient; intended owner requires aal2; narrow pending-tenant exception | T03 consume + T02 membership + initial T01 activation + T04/T22 atomic; replay/digest and last-owner checks |
| Revoke operator membership | Restricted Abdo platform/custodian command at aal2; never a tenant-owner UI in Phase 1 | Lock tenant/target membership; operator target only; no owner transfer/removal, self-elevation or content result; T02/T04/T22 atomic |
| Login/recovery/MFA/logout | Same-app Server Actions and technical callback | Provider session operations, origin checks; security-event recording/reconciliation, no membership writes from frontend Auth success |
| K03 reads | Page DAL / request-bound adapter with user JWT | Fresh session/current membership/role/assurance; safe columns, RLS, no service role |
| K04 artifact read | GET/HEAD handler with same user context | Derive bucket/key from authorized file and revision, recheck Storage authorization for each new request |
| Controlled synthetic seed | Custodian-reviewed nonproduction operational process only, through the dedicated seed command/role | Exact project/tenant allowlist, pre-generated IDs/digests, verified object upload then atomic DB linkage; no browser seed endpoint, generic service-role read adapter or client Storage DML |
| K05/K06/K07–K12 beyond above | Disabled/deferred | No reset, transfer, business command, general upload, notification or worker privilege in Phase 1 |

Server Actions use framework origin controls plus explicit authorization; POST cookie handlers require same-origin/CSRF defenses. Auth callback uses verified code/PKCE/provider token flow and strict redirects, not an arbitrary POST nonce. Bearer Edge endpoints independently verify JWTs and grants; CORS is not authentication. A trusted Auth-delivery progress callback cannot accept a client assertion that email was delivered; bind it to the operation and trusted workload. No generic role-setting/SQL proxy.

Before P1C migration execution, publish a command grant matrix. The membership command role must have only the column-level `SELECT`/`UPDATE(updated_at)` privileges and tenant-scoped policies needed by the invoker `lock_membership_tenant` and deferred `require_active_owner` triggers. The restricted suspension/revocation role may update only the explicitly allowed status columns after function-level transition checks; it cannot change tenant identity, `is_demo`, name or owner role. `WITH CHECK` must pin protected tenant fields, and direct attempts to widen those fields must fail. If the invoker-trigger coupling cannot be made safe with these narrow grants, stop and use a separately reviewed lock helper; never add broad table-owner or bypass-RLS access.

Canonicalize each command payload before hashing. Receipt uniqueness is tenant/actor/kind/key, with global provisioning scoped by actor/key. Same key and digest returns the original permitted result, no repeated business mutation/success audit; changed digest is conflict. Recheck authorization before returning private receipt data. Preserve attempt evidence separately. Audit failure aborts DB mutation; failure telemetry must not claim success. Auth events cannot be rolled back by Postgres, so record/reconcile partial outcomes explicitly.

## 9. Private Storage and linked-object ownership

The existing bucket is `phase-one-artifacts`, private. Allocate the `file_objects.id` first, then construct the server-generated key `tenant_id/file_object_id/opaque_uuid`; the immutable row cannot be created after upload with a different identifier. The Storage object policy must require its own current-membership/assurance predicate in addition to the exact bucket/key, published T17 and authorized T11 revision link. Parent DB policies must not query Storage, avoiding recursion. This direct predicate remains protective even if a later permissive `file_objects` SELECT policy is accidentally introduced; P1F tests that invariant.

K04 accepts tenant/file identifiers only, never a URL, bucket or raw object key. Stream using the requesting user's JWT, safe content headers, private/no-store caching and no shared CDN cache. Sanitize filenames; prevent active-content execution and path/header injection; abort cleanly on missing bytes, revoked access or upstream failure. Apply authorization to GET, HEAD and any range request. No public URLs, signed-link endpoint, listing or browser uploads. Direct authenticated object retrieval may succeed for the same authorized member; direct cross-tenant/anonymous/revoked reads and all client writes/signing/listing must fail. Downloaded bytes cannot be revoked.

Controlled seed is not general upload: pre-reviewed synthetic bytes, exact project/tenant scope, no public writer and no published overwrite. The dedicated seed command validates the pre-generated `file_id`, object key, digest, byte length and tenant graph, uploads with its protected server credential, and inserts the immutable published metadata/link only after verification. Reconcile Storage success/DB failure using recorded object identity and digest; leave unlinked bytes unreadable, retry DB linkage safely, and do not delete as an automatic cleanup workaround. DB link with missing bytes returns unavailable, never a fake preview. Published metadata is immutable; replacement means a new object/revision. D10 governs later cleanup.

Later K10 needs D17/D19: bounded upload intent, quarantine, allowed type/size/content validation and scanning, provenance/digest, immutable finalization and tenant-scoped orphan reconciliation. No guessed quotas, scanner, vector store or retention policy. The Phase 1 `storage.allow_any_operation` dependency is a managed Supabase behavior, not a local stub guarantee: P1A/P1E must verify its target semantics and fail closed if the helper is missing or behaves differently. A later signed-link helper, if approved, has A06's central five-minute maximum; it is excluded now.
